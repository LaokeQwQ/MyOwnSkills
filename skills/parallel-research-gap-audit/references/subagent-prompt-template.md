# 子代理提示词模板

三份模板：基线代理、分域代理、失败后窄化重跑。复制过去改占位符就能用。

占位符写法：`{{尖括号}}` 是要替换的内容。

模板里的每条约定后面都写了「为什么」，派发时可以把理由一起带上。子代理知道理由之后，在边界情况下会自己做出正确判断，而不是机械照做。

---

## 模板一：基线代理（只读代码，不做外部调研）

这个代理必须**先派**，或者和其他代理同轮派出但在提示词里说明基线报告的路径。它的产出是其他所有代理查重的依据。

```
你的任务：盘点 {{仓库名}} 在 {{能力范围}} 上的现有实现，产出一份查重基线报告。

严格只读：不要修改任何源文件或配置文件，不要跑构建、测试或任何会写入的命令。

先把报告写进 {{输出目录}}/00-{{主题}}-capability-inventory.md，写完之后再组织返回消息。
返回消息只要一段不超过 350 字的摘要，加上文件路径。如果你的输出预算不够，
文件本身就是交付物，宁可摘要写得极短，也不要在报告没写完的情况下去写摘要。

报告要求：

1. 开头写明性质：只读调研，未改动任何代码或配置。
2. 给出主流程全貌。按实际执行顺序列出各个阶段，每个阶段标注负责它的文件和行号。
   读者应该能照着这份清单在代码里走一遍。
3. 逐项列出已有能力。每一项都要有证据：文件路径加行号，或者测试函数名。
   写不出证据的，标成「未确认」，不要写成结论。
4. 单列一节「逐条盲区判定」。把 {{能力范围}} 里可能涉及的每一项都列出来，
   逐项写「有 / 没有 / 部分有」，并给出判断依据。
   这一节是后续所有分域代理查重的直接依据，宁可长，不要漏。
5. 如果代码里有注释明确写了某个能力「刻意不做」或「不在建模范围内」，
   原文引出来并注明位置。这类信息决定了缺口是「遗漏」还是「有意的设计选择」，
   两者的处理方式完全不同。
6. 结尾约定路径简写规则（例如「下文 {{某个短名}}.go 指 {{完整路径}}」），
   让后面的报告能写得简洁又不产生歧义。

行号以当前工作区的代码为准，并在报告里注明这一点。
```

## 模板二：分域代理（外部调研 + 与基线查重）

```
你的任务：调研 {{域名}} 这个方向上 {{时间范围}} 的全部 {{主题}}，
并与 {{仓库名}} 的现有实现查重，产出缺口报告。

严格只读：不要修改任何源文件或配置文件，不要跑构建、测试或任何会写入的命令。

先把报告写进 {{输出目录}}/{{编号}}-{{域名}}.md，写完之后再组织返回消息。
返回消息只要一段不超过 350 字的摘要，加上文件路径。如果你的输出预算不够，
文件本身就是交付物，宁可摘要写得极短，也不要在报告没写完的情况下去写摘要。

查重基线在 {{输出目录}}/00-*-capability-inventory.md，先读它，再开始调研。
基线里已经写了现有能力有哪些，你的报告不要重复建议已经实现的东西。

报告要求：

1. 开头用几行写清：域是什么、日期、优先级怎么定义（例如 P0 必做 / P1 应做 / P2 辅助）、
   与基线的关系。
2. 主体按 {{组织方式，例如年份 / 子类 / 技术栈}} 展开。每一项都要写清：
   - 外部资料里的原始形态（具体特征、字段、语法、请求形状）
   - 对应的标识符（编号、版本、公告）
   - 如果要做，落地时的误报风险或采纳成本，以及怎么压低它
3. 证据纪律：
   - 对仓库现状的每条判断，给文件路径加行号，或者测试函数名。给不出证据就写「未确认」。
   - 外部标识符（CVE、CWE、公告编号、版本号）凡不是从一手来源确认的，一律标「待核实」。
     来自二手来源的额外注明「二手来源」。
   - 编号查不到就留空并写「编号未确认」，不要凭印象填一个看起来合理的。
     编造编号比留空危害大得多：留空会被追问，编造会被采信。
   - 如果任务描述里给的编号或事实有误，直接纠正并说明依据，不要照着错的写。
4. 单列一节「明确做不到 / 不在范围内」。写清哪些情况原理上就无法覆盖，以及为什么。
   这一节的价值不低于缺口清单，它阻止后面的人往不可能有结果的方向投入。
5. 结尾给一节「可复用的模式抽象」。不要停在逐个案例，要从案例里抽出可以泛化的判定特征。
   这是报告最有长期价值的部分。

篇幅目标 300-800 行。超过 800 行说明域切得太宽，
请在返回摘要里说明你建议怎么拆，但不要自己拆。
```

## 模板三：失败后的窄化重跑

某个域的子代理报错、而且确认输出目录里没有可用文件时，用这份模板把它拆成两个更窄的代理。

拆窄的判断依据：一个域如果横跨多个技术生态、或者名字里带「全部」「所有」，就沿这个边界拆。
例如「结构化数据格式」可以拆成「XML 家族」和「JSON / 查询语言 / 表单结构」。

```
你的任务：调研 {{更窄的域}} 这个方向上的 {{主题}}，并与 {{仓库名}} 的现有实现查重。

这是上一轮 {{原域名}} 调研的窄化重跑。上一次失败的原因很可能是报告写完之后
返回摘要太长，超出了输出预算。所以这次特别注意下面这条：

**先把报告完整写进 {{输出目录}}/{{编号}}-{{窄域名}}.md，再写返回消息。
返回消息只要不超过 200 字的摘要加文件路径，不要复述报告内容，不要列要点清单。**
文件写完了，任务就算成功了。

严格只读：不要修改任何源文件或配置文件，不要跑构建、测试或任何会写入的命令。

查重基线在 {{输出目录}}/00-*-capability-inventory.md，先读它。
{{如果同域的另一个窄化代理已经产出，写上：}}
另外 {{编号}}-{{兄弟域名}}.md 覆盖了相邻的部分，先扫一眼它的目录，避免和它重复。

报告要求同分域代理：证据要给文件行号，外部标识符不确定的标「待核实」，
必须有一节写「明确做不到 / 不在范围内」，结尾给可复用的模式抽象。

篇幅目标 300-600 行。这次范围更窄，不要为了凑篇幅把邻近域的内容也写进来。
```

## 派发时的注意点

- **同一轮全部发出。** 分批发会让整合阶段干等，也容易出现后一批拿到过时基线的情况。
- **输出目录先建好**，并在每个提示词里写完整绝对路径。子代理对工作目录的假设经常和主代理不一致。
- **编号在派发时就定死**（`01-`、`02a-`、`02b-`……），不要让子代理自己起名。统一编号之后，整合报告的索引表能直接生成。
- **不要让子代理去派它自己的子代理。** 嵌套派发在这种任务里几乎总是失败，而且失败信息很难定位。
- **基线代理可以和分域代理同轮派出**，但要在分域代理的提示词里写明基线报告的路径，并告诉它「如果读的时候基线还没写完，就自己先扫一遍代码，不要跳过查重」。
